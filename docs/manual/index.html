SC 01

The big picture

Lyra is two programs sharing one body: a calm UI thread that draws and edits, and a strict audio thread that must hand the sound card a buffer every few milliseconds without ever being late. Everything else in this manual is detail on this one picture.

Animator's version. The Project is your exposure sheet. The views are you writing on it. The Bridge is the camera operator who re-reads the sheet every frame and only re-shoots what changed. The Engine is the projector: it runs at its own speed and can never stop to wait for you.
SC 02

Crates: five boxes, arrows only go down

The workspace is split so that each crate physically can't reach what it shouldn't. If lyra-model doesn't list the engine as a dependency, it can't accidentally start making sound.

lyra-plugin

The one interface every sound unit implements: built-in drums today, CLAP plugins later.

must never: depend on anything

lyra-dsp

Built-in instruments (M1 drums, M2–M3 synths and effects). Pure sound code.

must never: know about the engine or UI

lyra-engine

The audio thread: sequencer, channel mixing, the FIFOs, the atomics.

must never: allocate, lock or block in process

lyra-model

What a project is: channels, patterns, notes, undo history. Plain data.

must never: know about audio or UI

lyra-app

The window, views, theme, keyboard, sound card, and the bridge.

must never: send engine commands from views

SC 04

Two threads, three one-way pipes

The audio callback is treated like an interrupt handler on a microcontroller. Anything it will ever need is allocated beforehand on the UI thread and mailed over as a Box. There are no mutexes anywhere in the audio path.

Timing chart the first 50 ms after pressing Space (256-frame buffer at 48 kHz)

Animator's version. The audio thread is a projector running at a fixed frame rate. You slide finished cels into its tray (Commands), it hands the used ones back for you to wash (Trash), and a little frame counter on its side tells you where it is (atomics). It never stops to ask you anything.
SC 05

The life of a Box (storyboard)

Allocating and freeing memory can take unpredictable time, so the audio thread never does either. Here's how a new sequence (or a whole new channel) gets in and the old one gets out.

PANEL 1

Built. The UI thread allocates the new thing, e.g. compile() builds a Box<Sequence>. The engine is still playing the old one.

PANEL 2

Mailed. It travels through the Command FIFO inside Command::SetSequence. Only a pointer moves, nothing gets copied.

PANEL 3

Swapped. At its next callback the engine does mem::replace. The new one goes in, the old one comes out. No allocating, no freeing.

PANEL 4

Returned. The old Box goes back through the Trash FIFO. Next UI frame, collect_garbage() drops it on the UI thread, where freeing is safe.

Channels follow the same route: ChannelSlot::new (UI thread) calls the plugin's activate() and pre-allocates its event list (256), live-note queue (64) and two 256-frame buffers before the slot is mailed over as AddChannel. The engine itself reserves room for 128 channels up front, so adding one never allocates.

SC 08

The bridge: one direction, one place

Bridge::sync keeps a copy of the last project it sent. Every frame it compares, and for anything that changed it sends the smallest command that describes the change. If the channel list itself changed, it simply rebuilds every channel. That's simple and correct, and finer-grained updates can come later.

SC 10

Time: ticks, steps, and frames

All musical time is counted in ticks. PPQ = 96 ticks per quarter note, so 1 step = 24 ticks = a 16th note. The engine converts ticks into exact sample positions inside each block.

SC 11

Project data

lyra-model is plain data with no audio and no UI. The FL-style idea to remember: a step is a note. Lighting a step adds a one-step note at key 60. The piano roll (M2) will edit those same notes, so the two views can never disagree.

A step is a note

Undo History: a film strip of whole-project snapshots

Animator's version. Undo works like onion-skinning your entire scene. Before each change, a full copy of the Project goes on the stack. Undo just flips back one drawing. Projects are tiny right now, so this costs nothing, and it can never drift out of sync.

Plugins & the drum kit

Every sound unit implements one small trait. The engine doesn't care whether the sound comes from Lyra's own drums or (from M5 on) a hosted CLAP plugin. The badges show which thread is allowed to call each method.

pub trait Plugin: Send {
  fn name(&self) -> &'static str; ANY
  fn params(&self) -> &'static [ParamInfo]; ANY
  fn set_param(&mut self, id, value); UIAUDIO
  fn activate(&mut self, sample_rate); UI
  fn process(&mut self, ctx); AUDIO · REAL-TIME
}

Each drum keeps a small, fixed pool of voices so tails can overlap without allocating. Instrument ids like "lyra.kick" are saved in projects and are never renamed. An unknown id (say, a project from a newer Lyra) loads as a silent Silence placeholder instead of breaking the channel list.

SC 13

Hands: what the mouse and keys do

Every knob in Lyra works the same way, so your hands only have to learn it once. Keys are read by physical position, so the piano layout works the same on QWERTY, AZERTY and Dvorak.

Every knob

  • drag up / down: change
  • Shift + drag: fine
  • mouse wheel: nudge
  • double-click: reset to default

Channel rack

  • click / drag steps: paint. The first step you touch decides on or off, so one gesture never flickers
  • right-drag: erase
  • wheel on a lit step: velocity
  • Shift + wheel: pitch
  • right-click a name: fill every 2 / 4 / 8 · clear · delete
  • click the light: mute
  • right-click the light: solo (one at a time)

Keys

  • Space: play / stop
  • Esc: stop
  • ↑ / ↓: choose channel
  • Ctrl+Z: undo
  • Ctrl+Shift+Z · Ctrl+Y: redo

The typing keyboard is a piano plays the selected channel, live

SC 14

House rules

The short list that keeps Lyra from collapsing like the last four attempts. If a change breaks one of these, it's the change that's wrong.

process() is an interruptNever allocate, lock, free, print, touch files or wait on the audio thread. Do all of that in new() / activate().
Views only edit the projectbridge.rs is the only file that turns edits into engine commands. Live playing is the one exception.
Memory dies on the UI threadReplaced data goes back through the Trash FIFO. The engine never drops a Box itself.
A step is a noteThe rack and the piano roll edit the same Notes. There's no separate 'step data'.
Ids are foreverInstrument ids and parameter order are saved in projects. Add new ones, never rename or reorder.
Ticks agree everywheremain.rs refuses to compile if model and engine disagree on TICKS_PER_STEP.
Theme lives in one fileEvery colour and texture is in theme.rs. The generated textures are placeholders for hand-made art.
Safety clampThe master output is hard-clamped to ±1 to protect ears and speakers.

SC 16

Glossary

Words that show up in the code, with the animation equivalent where there is one.

tick
the smallest unit of musical time; 96 per beat. Like a sub-frame on your timing chart.
step
a 16th note = 24 ticks; one button in the channel rack. One cell on the X-sheet.
PPQ
pulses (ticks) per quarter note, here 96.
block / buffer
a slice of audio frames the sound card asks for at once (~256 ≈ 5 ms).
sample / frame
one instant of audio; 48,000 per second. A frame here means one sample on every speaker channel, not an animation frame!
FIFO / ring buffer
a one-way, fixed-size queue (rtrb). One writer, one reader, no locks.
atomic
a number both threads can read and write safely without a lock; the latest value wins.
Box
a single owned chunk of heap memory. Passing it around moves a pointer, not the data.
real-time safe
guaranteed to finish in bounded time: no allocation, locks, I/O or waiting.
choke group
channels sharing a group number cut each other off (closed hat silences open hat).
plugin
anything that turns events into sound (or sound into sound). Lyra's drums are plugins too.
CLAP
an open plugin standard Lyra will host in M5.
