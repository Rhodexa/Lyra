02

Two threads, three pipes

Lyra has exactly two threads that matter. The UI thread is your main loop: it draws a frame, handles the mouse, edits the project. The audio thread is your interrupt: the sound card calls it every few milliseconds and it must hand back a buffer on time, every time. They never share memory behind a lock. They talk through three one-way pipes.

In microcontroller terms. Engine::process is a DMA half-transfer interrupt: fill the next half of the buffer, return. The Command FIFO is the single-producer/single-consumer ring buffer you'd write from main() to the ISR. The Trash FIFO exists because free() is not ISR-safe either, so the ISR hands memory back to the main loop instead. Shared is a block of volatile status registers the ISR writes and the main loop polls. ChannelSlot::new is your init code sizing static buffers before interrupts are enabled.

Three details worth knowing crates/lyra-engine/src/lib.rs

  • The compiler enforces the split. lyra_engine::create(sr) returns (Engine, EngineHandle). audio.rs moves the Engine into the cpal closure (build_typed). After that the UI thread has no way to reach it at all, so the only route left is the pipes.
  • Peak meters without a lock. raise_peak does fetch_max on the raw u32 bits of a positive f32. That works because positive floats sort the same way as their bit patterns.
  • All atomics use Relaxed. Each value stands alone, and nobody needs two of them to be consistent with each other, so no memory fences are needed.
03

Life of an edit

You click a step in the channel rack. Here is everything that happens until you hear it, in order. The important part: the view only edits the Project. It never talks to the engine. The bridge notices the difference at the end of the frame and sends it.

#What actually happens
①rack.rs reads the mouse once per frame through ui.input(..) into a plain tuple (the egui lock rule, see section 09), then finds the step under the pointer with step_at().
②On the press only: h.checkpoint(p) clones the whole Project onto the undo stack and clears redo. It also sets st.paint = Some(!lit), so the first step you touch decides "painting on" or "painting off" for the whole drag.
③Every frame while the button is held: set_step(id, step, on, 0.8). Lighting a step pushes a Note { start: step × 24, len: 24, key: 60, velocity: 0.8 } and re-sorts. A step is a note. Dragging across more steps adds more notes, all under the one checkpoint.
④After all windows are drawn and keyboard actions are applied, LyraApp::update calls bridge.sync. This is the last thing in the frame.
⑤Bridge keeps last: Option<Project>, a full copy of what it saw last time, and last_target: Option<Playing>. The target is Playing::Pattern(index) or Playing::Song, chosen from UiState::song_mode. If both are unchanged (the usual case) it returns straight away. Otherwise it diffs field by field (table below).
⑥It compiles the target on every change. In pattern mode, compile() turns each Note of each channel, by index in p.channels, into a SeqNote { start, len, channel, key, velocity }, sorted by start, with length = play_length() × 24 ticks. In song mode compile_song() flattens the playlist (section 05). If the result equals last_seq and the channels were not rebuilt, nothing is sent. So renaming a channel or editing a pattern that isn't playing costs no command.
⑦eng.send(Command::SetSequence(Box::new(seq.clone()))), then last_seq = Some(seq) and last = Some(p.clone()). The Box was allocated here, on the UI thread.
⑧–⑨At the start of its next callback, Engine::process runs drain_commands(). SetSequence does mem::replace(&mut self.seq, seq), which only swaps a pointer, then wraps pos and start_marker into the new length.
⑩The old Box goes into the Trash FIFO via discard(Trash::Sequence(old)). The audio thread never frees memory.
⑪schedule() plays from the new list. Notes that were already sounding keep their own countdown in held, so swapping the list can never leave one hanging (section 04).
⑫Next frame, read_engine() calls collect_garbage(). That pops the trash, and dropping the popped value frees the old sequence here on the UI thread.

Song mode needs no engine code. The engine only ever plays one looping Sequence. In song mode the bridge simply compiles the whole playlist into one long one (section 05).

Life of a block of audio

Every time the sound card wants samples, the cpal callback in audio.rs calls Engine::process(out, channels). This is the whole of it. Everything in this section runs on the audio thread, with nothing allocated, nothing locked and nothing waited on.

Inside schedule(): held notes Engine::schedule

Drums ignore note length, but the synth needs a NoteOff. The engine keeps a small held list per channel of Held { key, remaining }, where remaining is in ticks. It sends the NoteOff itself when the count runs out, so the note-off doesn't depend on the sequence still containing the note.

05

Time

All musical time is an integer number of ticks. PPQ = 96 ticks per quarter note, so a 16th note (one step) is 24 ticks, a beat is 96 and a 4/4 bar is 384. Samples only appear inside schedule(), at the last moment.

Loop wrap Engine::schedule, offset_of

Dynamic pattern length Pattern::play_length (lyra-model/src/lib.rs)

Song mode: the playlist becomes one long loop bridge.rs compile_song · lyra-model Clip

  • Clip { pattern: PatternId, track, start, len } (ticks). It points at a pattern by its stable id, so cloning or reordering patterns never makes a clip play the wrong one (test clips_keep_pointing_at_the_right_pattern).
  • For each clip on an unmuted track, the pattern repeats every play_length() × 24 ticks to fill the clip. A note that runs past the clip's end is cut there (len.min(clip.len − at)). Notes starting beyond the pattern's own length are skipped. Tests: a_long_clip_repeats_its_pattern, muted_tracks_and_clip_ends_are_respected.
  • song_length() runs to the end of the last clip, rounded up to whole bars and at least one bar.
  • While the song plays, the rack and piano roll still show a playhead inside the current pattern. app.rs pattern_position() finds a clip of that pattern under the playhead and uses (playhead − clip.start) % loop_len. If no clip of that pattern is playing, they show no playhead.

06

The plugin interface

Every sound in Lyra comes through one trait. Built-in drums and the synth implement it today, and hosted CLAP plugins will be wrapped to look the same. So the engine never cares where sound comes from, and the editor never cares what the instrument is.

pub trait Plugin: Send { fn name(&self) -> &'static str; // any "Lyra Synth" fn params(&self) -> &'static [ParamInfo]; // any static table, id = index fn groups(&self) -> &'static [ParamGroup] {..} // any layout hint (default: none) fn set_param(&mut self, id: u32, value: f32); // audio via Command::SetParam fn activate(&mut self, sample_rate: f32); // UI in ChannelSlot::new, before it travels fn process(&mut self, ctx: ProcessContext<'_>); // audio REAL-TIME: treat it like an ISR } pub struct ProcessContext<'a> { sample_rate: f32, events: &'a [TimedEvent], // sorted by offset out_l: &'a mut [f32], // OVERWRITE every sample, don't add out_r: &'a mut [f32], } pub struct TimedEvent { offset: u32, event: Event } // offset = sample inside this block pub enum Event { NoteOn { key: u8, velocity: f32 }, NoteOff { key: u8 }, AllNotesOff }

ParamInfo::new(id, name, min, max, default, unit, curve)

A continuous knob. Values are stored in real units (Hz, seconds, 0..1). Curve::Linear or Curve::Exponential: with exponential, equal knob travel gives an equal ratio, which is right for frequencies and times. to_normalized / from_normalized map between the 0..1 knob position and the real value. is_bipolar() (min < 0 < max) makes the knob draw from the middle. format() picks the display from unit: "1.20 kHz", "45 ms", "L 30", "+3 st".

crates/lyra-plugin/src/lib.rs

ParamInfo::choice(id, name, labels, default)

A menu. labels is non-empty, and the value is an index stored as f32 (min = 0, max = labels.len() − 1). from_normalized rounds it. is_choice() is what tells the editor to draw a combo box instead of a knob.

ParamGroup { name, ids: Range<u32> } names a run of ids, for example "Filter" = 6..11. It is only a layout hint.

  • Drums (drums.rs) each keep a fixed array of 4 voices, used round-robin, so tails overlap. Every hit fades in over 24 samples (DECLICK). NoteOff is ignored, because drums are one-shots. AllNotesOff sets a 3–4 ms fade, which is how chokes and Stop silence them. They are mono and use util::run_mono, which applies events at their exact sample.

The p module (p::CUTOFF, …) names the ids, so presets read clearly.

What is not in the Project app.rs UiState · piano_roll.rs PianoRoll

View state is not saved and not undoable. The startup song crates/lyra-app/src/demo.rs

The demo is a deep-house groove in A minor at 124 bpm with swing 0.15. It has seven channels: Kick, Clap, Closed hat, Open hat (both hats in choke group 1, so the closed hat cuts the open one), Snare (ghost notes), Bass (Deep Bass preset), and Chords (Chord Stab, Am7 then Fmaj7). 09

Rules that keep Lyra alive

Earlier attempts died partly from losing track of what the code was doing. These rules are what keep this one readable. Each is short, checkable, and already followed by the code, so breaking one shows up in review.

1 · The audio callback is an ISR

Inside Engine::process and every Plugin::process: no allocating, no freeing, no locks, no files, no printing, no waiting.

How the code obeys it: every Vec is created with_capacity beforehand. Every push is guarded by len < capacity. It uses drain(..), swap_remove, and an in-place sort_unstable_by_key. Replaced data goes to the Trash FIFO. The only Mutex anywhere near audio is in the test plugin Recorder.

lyra-plugin/src/lib.rs (module docs) · lyra-engine/src/lib.rs

2 · Build it on the UI thread, send a Box

Anything big is allocated and prepared on the UI side: ChannelSlot::new calls plugin.activate(sr) and sizes all buffers, and the bridge compiles the Sequence. It crosses as one pointer. The old one comes back as trash.

ChannelSlot::new · Bridge::sync · Engine::discard

3 · The egui lock rule

Never call another ctx / ui.ctx() method inside a ctx.input(|i| …) closure. The same goes for memory, data and the other closure accessors. egui's context lock is not re-entrant, so the nested call waits on itself forever.

Copy what you need out into a tuple first, then call. This froze the app on the first click in v0.1 (fixed in 3ba6958). clicked_inside() in app.rs carries the warning, and rack.rs and piano_roll.rs read input as one tuple at the top.

app.rs clicked_inside · rack.rs show · piano_roll.rs show

4 · Views edit the project. bridge.rs talks to the engine.

rack.rs, piano_roll.rs, playlist.rs, editor.rs and transport.rs only change Project (and UiState). Bridge::sync is the one place edits become Commands: one direction, one place.

The only exceptions are actions, not edits: Play, Stop, Seek and live notes. Views push those as Actions, and app.rs apply() sends them. Even PAT/SONG is just UiState::song_mode. The bridge reads it as its Playing target.

bridge.rs (module docs) · app.rs apply

5 · Parameter ids never move

A parameter's id is its index in params(). Projects store params: Vec<f32> by index, and presets store (id, value) pairs. So new parameters are appended, never inserted or renumbered. The editor fills a too-short list with defaults, which only works if new ones are at the end.

Instrument ids ("lyra.kick") are saved in projects and never renamed. An unknown id becomes Silence rather than an error.

lyra-plugin docs · lyra-dsp INSTRUMENTS · editor.rs show

6 · Checkpoint before, once per gesture

Call History::checkpoint(&project) before the change, on the press or drag start, not on every frame of a drag. For knobs, use rack::tracked().

lyra-model History · rack.rs tracked

7 · Arrows only point down

lyra-model and lyra-plugin depend on nothing. lyra-dsp knows only lyra-plugin. lyra-engine knows only lyra-plugin (plus rtrb). Nothing below lyra-app may import a crate above it.

crates/*/Cargo.toml

8 · Looks live in theme.rs

Colours, sizes (Metrics) and textures live only in theme.rs. Borders and details are darker than their surfaces (LINE). Only selected or active things get a bright edge. Generated textures are placeholders for hand-made art.
